# SOC Detection Lab — Splunk & Metasploitable2

A hands-on SOC detection and incident investigation lab built with Splunk. The project simulates the exploitation of a vulnerable FTP service on Metasploitable2, collects the resulting security telemetry, detects suspicious activity using SPL, investigates the associated events, and configures automated alerting.

This project demonstrates the workflow of a security operations environment from **attack simulation → log collection → detection → investigation → alerting → incident response**.

---

## 🎯 Objectives

- Deploy and configure Splunk as a SIEM platform
- Configure centralized syslog collection over UDP 514
- Monitor FTP activity generated by a vulnerable vsftpd service
- Simulate exploitation of vsftpd 2.3.4 using Metasploit
- Develop SPL-based detection logic
- Investigate security events and identify the originating host
- Configure automated Splunk alerting
- Document a SOC-style incident response process

## 🔴 Attack Simulation
The lab used Metasploit to simulate exploitation of the intentionally vulnerable vsftpd 2.3.4 FTP service running on Metasploitable2.

- The following Metasploit module was used:
  exploit/unix/ftp/vsftpd_234_backdoor

- The target and attacker hosts were configured as:
    - Attacker / Splunk Host:
      192.168.92.145

    - Target:
      192.168.92.144

The purpose of the attack simulation was not simply to demonstrate exploitation, but to generate realistic security activity that could subsequently be detected and investigated from a defensive SOC perspective.

## 📥 Log Collection
Splunk was configured to receive syslog telemetry from Metasploitable2 over UDP port 514.

- The vulnerable FTP service generated connection activity in:
/var/log/vsftpd.log

- Example connection evidence:
CONNECT: Client "192.168.92.145"

A controlled syslog test was also performed to verify that telemetry could successfully travel from Metasploitable2 to Splunk.

- Splunk received the events using:
Source: udp:514
Source Type: syslog

## 🔎 Detection

- A Splunk SPL query was created to identify FTP connection activity recorded by vsftpd:
index=* sourcetype=syslog "CONNECT: Client"

The query identifies events containing the CONNECT: Client pattern and allows the analyst to investigate the originating host.

- Example detected activity:
CONNECT: Client "192.168.92.145"

The detection confirmed that activity originating from the Kali host was recorded by the vulnerable FTP service and successfully ingested into Splunk.

## 🕵️ Event Investigation

The detected event was expanded and analyzed in Splunk to examine the available event fields and verify the telemetry source.

Key investigation points included:

- Source IP address
- FTP connection activity
- Syslog source
- UDP 514 ingestion
- Event timestamp
- Relationship between the attacker and target systems

- The originating host was identified as:
192.168.92.145

- The target system was:
192.168.92.144

The investigation demonstrated how a SOC analyst can move from a detection query to the underlying event and establish the context surrounding suspicious activity.

## 🚨 Automated Alerting

- A scheduled Splunk alert was configured using the detection query:
index=* sourcetype=syslog "CONNECT: Client"

- The alert was configured to trigger when:

- Number of Results > 0

- The alert was named:
FTP Connection from External Host

The alert demonstrates how detected activity can be converted into an automated SOC notification rather than relying exclusively on manual log searches.

## 🛡️ SOC Incident Response

If this activity were observed in a production environment, the following response workflow could be applied:

1. Validate: Confirm the source and destination IP addresses and determine whether the FTP connection was authorized.

2. Investigate: Correlate the FTP connection with other available logs and security telemetry to determine whether exploitation or additional malicious activity occurred.

3. Contain: If unauthorized activity is confirmed, isolate the affected system and restrict the source of the malicious traffic where appropriate.

4. Eradicate: Remove the vulnerable service or upgrade it to a secure version. Investigate for persistence, unauthorized accounts, or other signs of compromise.

5. Recover: Restore affected services to a secure state and continue monitoring for recurring activity.

6. Document: Preserve relevant logs, document the timeline and indicators of compromise, and record the actions taken during the investigation.
